#+title: Building UIs In Nest

Nest is an immediate-mode user interface library. An interface is a tree of widgets declared from the application's own state on every frame; nothing is retained between frames except the state you hold and the small amount the library keeps for you. Sizes and positions are solved from constraints, and ~fixed~ sizes, ~pin~ and raw constraints are there when a declaration needs exact geometry.

A widget is a routine, not a type. It takes the state it draws from, declares its children, and returns the events that happened inside it, so widgets compose the way procedures compose. Each widget that owns state declares its own state type, its own event type and its own ~update~; there is no single application model. Every widget the library ships with is shown in the gallery, ~apps/gallery/gallery.nim~ (~nimble gallery~).

Two front ends build the same tree, over the same widgets, the same solver and the same frame loop.

The *Nim API* is a set of macros and procedures compiled into the program. Widgets are declared with the ~widget~ macro, and each widget's state and events are ordinary Nim types.

The other front end is *[[https://github.com/dneumann42/owl][owl]]*, a general-purpose command-oriented language. ~src/nest/owldsl.nim~ defines a DSL in owl — commands for widgets, layout, state and events, alongside the language's own - so an interface can be written as owl source instead of Nim. A project written that way is a directory of ~.owl~ files run by the ~nest~ executable: nothing is compiled, and a file that changes on disk is re-read on the next frame.

Most of what follows uses the Nim API, since that is where the types are visible; [[*The Owl DSL][The Owl DSL]] covers the owl side and where the two differ. Layout constraints are in [[file:layout.org][layout.org]], dialogs and overlays in [[file:dialogs.org][dialogs.org]], and the API reference is generated by ~nimble docs~.

* A Complete Application

A counter, and a parent that keeps a tally of what the counter has done. Two widgets, each with its own state type, its own event type and its own ~update~.

#+begin_src nim
import nest

type
  Counter = object
    count: int
    step: int

  CounterEvent = enum
    Incremented
    Decremented
    StepChanged

  App = object
    counter: Counter
    changes: int
    highest, lowest: int

  AppEvent = enum
    CountChanged
    HistoryCleared

proc update(model: var Counter, event: CounterEvent) =
  case event
  of Incremented: model.count += model.step
  of Decremented: model.count -= model.step
  of StepChanged: model.step = if model.step == 1: 5 else: 1

proc update(model: var App, event: AppEvent) =
  case event
  of CountChanged:
    inc model.changes
    model.highest = max(model.highest, model.counter.count)
    model.lowest = min(model.lowest, model.counter.count)
  of HistoryCleared:
    model.changes = 0
    model.highest = model.counter.count
    model.lowest = model.counter.count

widget counter(model: Counter) emits CounterEvent:
  ui.column(ui.id("root"), cfg(width = fit(), height = fit(), gap = 8, alignItems = Center)):
    ui.label(ui.id("count"), $model.count)
    ui.row(ui.id("controls"), cfg(width = fit(), height = fit(), gap = 8, alignItems = Center)):
      if ui.button(ui.id("dec"), "-", width = fixed(32)):
        emit Decremented
      if ui.button(ui.id("inc"), "+", width = fixed(32)):
        emit Incremented
      if ui.button(ui.id("step"), "step " & $model.step):
        emit StepChanged

widget counterApp(model: var App) emits AppEvent:
  ui.panel(ui.id("root"), cfg(padding = 16, gap = 12, alignItems = Center, justifyContent = Center)):
    ui.label(ui.id("title"), "Counter")

    for event in ui.counter(model.counter):
      model.counter.update(event)
      if event != StepChanged:
        emit CountChanged

    ui.label(ui.id("stats"), $model.changes & " changes, range " & $model.lowest & " to " & $model.highest)
    if ui.button(ui.id("reset"), "Reset history"):
      emit HistoryCleared

when isMainModule:
  runApp(AppConfig.init(width = 360, height = 220, title = "Counter"),
      App(counter: Counter(step: 1)), update, counterApp)
#+end_src

~counter~ reads a ~Counter~ by value and reports what happened — ~Incremented~, ~Decremented~, ~StepChanged~. It does not change the count, and it has no reference to the ~App~ above it.

~counterApp~ holds the ~Counter~ as a field, passes it down, and reads back the events the call returns. For each one it calls the counter's own ~update~, which is the only routine that writes to a ~Counter~, then decides whether the event means anything at this level. Two of the three do, and become ~CountChanged~, which is ~counterApp~'s vocabulary rather than the counter's; ~StepChanged~ stops here.

~runApp~ opens the window and runs the frame loop: it holds the ~App~, calls the root widget once per frame, and applies each event the frame collected with ~update~. ~update~ is overloaded on the state type, so the call inside ~counterApp~ and the call inside ~runApp~ resolve to different procedures.

The ordering is worth noting. ~counterApp~ applies the counter's events as it runs; ~runApp~ applies ~counterApp~'s events after it returns. By the time ~update(App, CountChanged)~ runs, ~model.counter.count~ already holds the new value, which is why ~highest~ and ~lowest~ can read it directly.

* Architecture

** Widgets Are Routines

~widget name(params): body~ expands to a routine taking ~var UI~ as its first parameter, with the body wrapped in an id scope. There is no base class, no virtual dispatch and no registration, and a ~widget~ declaration and a hand-written ~proc name(ui: var UI, ...)~ are interchangeable. A widget that declares an event type returns the events it emitted; one that does not returns nothing.

Widgets are therefore composed like procedures. Declaring a child is a call, giving it state is an argument, and reusing a widget twice in one frame is two calls in two id scopes.

** State And Events

State and events are declared per widget rather than per application. A widget that owns state has a state type, an event type, and an ~update~ that applies one event to one value of that type. Its parent holds that state as a field and calls that ~update~; the root state type is whatever the composition adds up to, and ~runApp~ holds one value of it.

Two rules keep this from becoming a graph of references:

- A widget reads its own state and its children's, and writes only through the ~update~ of the state it owns.
- A widget never touches a sibling's state. Two children meet in their parent.

A state type, an event type, an ~update~ and a widget are a self-contained unit, which is what makes a subtree movable between applications.

An event names what happened inside the widget that emitted it, in that widget's terms: ~SavePressed~, not ~SaveTheDocument~. The caller either handles it or emits one of its own in its place, so a child's event type stays private to the child and each level is translated at the boundary where both vocabularies are in scope.

** Frames And Passes

A frame makes two passes over the declarations. The event pass dispatches the input collected since the last frame. The layout pass builds the tree that is measured, solved and drawn. Calls are gated on the pass they are meaningful in: ~ui.button~ reports a click in the event pass and adds a button in the layout pass, ~ui.label~ does nothing in the event pass, and a ~ui.events:~ block runs in the event pass only.

Two consequences carry into everything else. State must change in the event pass, or the change applies twice. And a declaration cannot depend on a value the layout pass produces, because the event pass has already run with the previous one. [[*The Frame][The Frame]] has the rest.

Input is recorded while a frame updates its widgets and read on the next frame's event pass, so a press becomes a click one frame later. Nest schedules that frame itself.

** Identifiers

The tree is rebuilt every frame, so per-widget state that has to survive — focus, scroll offsets, text cursors, selections, an in-progress drag — is held by the ~UI~ and keyed by widget identifier. ~ui.id~ derives an identifier from its arguments and the id scopes enclosing the call, so the same declaration yields the same identifier on every frame.

Identifiers must be stable, not merely distinct. One built from a loop index refers to a different item once the list is reordered, and the retained state stays with the position instead of the item; derive it from something belonging to the data.

** Layout And Sizes

Sizes and positions come from a Cassowary solver. Container declarations state relationships — direction, gaps, padding, alignment, size policies — and the solver satisfies them at the current window size, so resizing re-solves rather than re-runs different code. ~fixed~ sizes, ~pin~ and raw constraints on ~ui.layout~ express exact geometry where a relationship is not what is wanted.

Every widget carries a default size policy, so most declarations name no size at all; see [[*Sizes Have Defaults][Sizes Have Defaults]]. The solver itself is documented in [[file:layout.org][layout.org]].

** Redraws

Frames are demand-driven: with no input and no outstanding request, no frame runs and the previous one stays on screen. ~ui.requestRedrawAfter~, ~ui.markDirty~, ~ui.markAllDirty~ and ~ui.markRealtime~ ask for frames. ~runApp~ marks the frame dirty whenever it applied an event, so ordinary interaction needs no request; a clock that ticks once a second costs one frame a second.

* Widgets

~widget name(params): body~ declares a portion of an interface. It expands to a routine that takes the ~UI~ as its first parameter and runs the body inside ~ui.scope("name")~.

#+begin_src nim
import nest

type Counter = object
  count: int

widget counterLabel(model: Counter):
  ui.label(ui.id("count"), $model.count)

proc counterLabelByHand(ui: var UI, model: Counter) =
  ui.scope("counterLabelByHand"):
    ui.label(ui.id("count"), $model.count)
#+end_src

The two declarations above are equivalent. The body is ordinary Nim, every call keeps its ~ui.~ prefix, and turning a widget into a procedure or back is a change to the header only. No type is declared, and nothing in the body has to move.

** Ids Are Scoped By The Widget

Because the body runs inside ~ui.scope("name")~, two widgets can both use ~ui.id("row")~ without meeting.

#+begin_src nim
import nest

widget header(title: string):
  ui.row(ui.id("row"), cfg(width = fill(), height = fit(), gap = 8)):
    ui.label(ui.id("text"), title, width = fill())

widget footer(text: string):
  # `ui.id("row")` here is a different id from the one in `header`.
  ui.row(ui.id("row"), cfg(width = fill(), height = fit(), gap = 8)):
    ui.label(ui.id("text"), text, width = fill())

widget page():
  ui.column(ui.id("root"), cfg(width = fill(), height = fill(), gap = 6)):
    ui.header("Title")
    ui.footer("Status")
#+end_src

The scope covers the widget's name, not its arguments, so declaring the same widget twice in one frame still needs a scope at the call site.

#+begin_src nim
import nest

widget pane(title: string):
  ui.panel(ui.id("root"), cfg(width = fill(), height = fill(), padding = 8)):
    ui.label(ui.id("title"), title, width = fill())

widget splitView():
  ui.row(ui.id("root"), cfg(width = fill(), height = fill(), gap = 8)):
    ui.scope("left"):
      ui.pane("Left")
    ui.scope("right"):
      ui.pane("Right")
#+end_src

Reaching a widget's id from outside means entering its scope, which is how a caller finds a widget it did not declare itself.

import nest

proc focusSearch(ui: var UI) =
  ui.scope("searchBox"):
    ui.focus(ui.id("input"))
#+end_src

** When To Write A Plain Procedure

~widget~ adds a ~ui~ parameter and an id scope. Write a plain procedure when neither is wanted: for code that computes rather than declares, and for a helper that must share the caller's id scope.

#+begin_src nim
import nest

type Task = object
  title: string
  done: bool

proc summary(tasks: seq[Task]): string =
  var done = 0
  for task in tasks:
    if task.done:
      inc done
  $done & " of " & $tasks.len & " done"

proc rowLabel(ui: var UI, key, text: string) =
  ui.label(ui.id(key, "label"), text, width = fill())

widget taskList(tasks: seq[Task]):
  ui.column(ui.id("root"), cfg(padding = 8, gap = 4)):
    ui.label(ui.id("summary"), tasks.summary, width = fill())
    for task in tasks:
      ui.rowLabel(task.title, task.title)
#+end_src

* The Frame

~ui.layout~ runs its body twice.

| Pass   | Purpose                     | ~ui.inEventPhase~ | ~ui.inLayoutPhase~ |
|--------+-----------------------------+-----------------+------------------|
| event  | dispatch last frame's input | true            | false            |
| layout | build the widget tree       | false           | true             |

Widget calls behave differently in each pass. ~ui.button~ returns whether it was clicked during the event pass and builds a button during the layout pass. Declaration-only calls such as ~ui.label~ do nothing during the event pass.

#+begin_src nim
import nest

widget passProbe(log: var seq[string]):
  if ui.inEventPhase:
    log.add "event pass"
  else:
    log.add "layout pass"
  ui.label(ui.id("hello"), "hello")
#+end_src

Three rules follow from the double pass:

1. State changes belong in the event pass. Code that runs in both passes would apply a change twice.
2. Declarations must not depend on anything the layout pass changes, because the event pass has already run with the previous values.
3. Events are emitted during the event pass. Consume them where they are returned, or accumulate them with ~add~; assigning them to a variable that outlives the call loses them, because the layout pass runs the widget again and returns nothing.

A local whose name matches one of the ~ui.~ routines shadows it: a variable called ~events~ breaks ~ui.events~, and a loop variable called ~row~ breaks ~ui.row~. Name an event queue ~emitted~, and a loop index ~rowIndex~.

~ui.events:~ marks a block as event-pass only.

#+begin_src nim
import nest

widget quitHint(quitRequested: var bool):
  ui.events:
    if ui.keyPressed("Escape"):
      quitRequested = true

  ui.label(ui.id("hint"), "Press Escape to quit")
#+end_src

Interaction is recorded when a frame updates its widgets, and observed on the next frame's event pass. A press therefore becomes a click one frame later; Nest requests that frame itself, so no polling is needed.

#+begin_example
frame 1 no input   : count=0 drawn=[-,0,+]
frame 2 press on + : count=0 drawn=[-,0,+]
frame 3 held       : count=1 drawn=[-,1,+]
frame 4 release    : count=1 drawn=[-,1,+]
#+end_example

Frame 2 records the press. Frame 3 observes the click, applies ~Incremented~, and draws ~1~ in that same frame.

* Events Between Widgets

A widget declares its own event type with ~emits~ and reports one with ~emit~. The events it emitted are its return value, so its caller sees exactly what happened inside it and nothing else.

#+begin_src nim
import nest

type
  ToolbarEvent = enum
    NewPressed
    OpenPressed
    SavePressed

widget toolbar(modified: bool) emits ToolbarEvent:
  ui.row(ui.id("root"), cfg(width = fill(), height = fit(), gap = 6, padding = 6)):
    if ui.button(ui.id("new"), "New"):
      emit NewPressed
    if ui.button(ui.id("open"), "Open"):
      emit OpenPressed
    if ui.button(ui.id("save"), "Save" & (if modified: " *" else: "")):
      emit SavePressed
#+end_src

** Changing State In A Handler

A widget's body runs twice a frame, so a handler that changes state has to say when it applies. ~ui.events~ is that guard: it runs only on the event pass. ~emit~ needs no guard, because the loop applies what it collected once.

Widget helpers report only on the event pass, and so do ~ui.clicked~ and ~ui.submitted~, so a handler written against those runs once by itself. The guard is what makes a change that goes through anything else, such as a value read out of a widget, safe.

#+begin_src nim
import nest

type
  Filters = object
    caseSensitive: bool
    matches: int

  FiltersEvent = enum
    CaseToggled

proc update(model: var Filters, event: FiltersEvent) =
  case event
  of CaseToggled: model.caseSensitive = not model.caseSensitive

widget filters(model: Filters) emits FiltersEvent:
  ui.column(ui.id("root"), cfg(width = fit(), height = fit(), gap = 4)):
    ui.checkbox(ui.id("case"), "Case sensitive", model.caseSensitive)
    if ui.clicked(ui.id("case")):
      emit CaseToggled

widget search(model: var Filters) emits FiltersEvent:
  ui.column(ui.id("root"), cfg(width = fill(), height = fit(), gap = 6, padding = 8)):
    for event in ui.filters(model):
      # Applied once a frame, not once a pass.
      ui.events:
        model.update(event)
      emit event
#+end_src

** Handling A Child's Events

A parent reads the events where the call returns them.

#+begin_src nim
import nest

type
  ToolbarEvent = enum
    NewPressed
    SavePressed

  Document = object
    text: string
    modified: bool

widget toolbar(modified: bool) emits ToolbarEvent:
  ui.row(ui.id("root"), cfg(width = fill(), height = fit(), gap = 6)):
    if ui.button(ui.id("new"), "New"):
      emit NewPressed
    if ui.button(ui.id("save"), "Save"):
      emit SavePressed

widget editorPane(model: var Document):
  ui.column(ui.id("root"), cfg(width = fill(), height = fill(), gap = 6)):
    for event in ui.toolbar(model.modified):
      case event
      of NewPressed:
        model.text = ""
        model.modified = false
      of SavePressed:
        model.modified = false
    ui.label(ui.id("text"), model.text, width = fill(), height = fill())
#+end_src

** Raising An Event Further Up

A parent that cannot answer a child's event emits one of its own in its place. The child's type stays private to the child; each level speaks its own vocabulary.

#+begin_src nim
import nest

type
  ToolbarEvent = enum
    NewPressed
    SavePressed

  PaneEvent = enum
    SaveRequested
    TitleChanged

widget toolbar() emits ToolbarEvent:
  ui.row(ui.id("root"), cfg(width = fill(), height = fit(), gap = 6)):
    if ui.button(ui.id("new"), "New"):
      emit NewPressed
    if ui.button(ui.id("save"), "Save"):
      emit SavePressed

widget pane(title: var string) emits PaneEvent:
  ui.column(ui.id("root"), cfg(width = fill(), height = fill(), gap = 6)):
    for event in ui.toolbar():
      case event
      of NewPressed:
        # Handled here: the shell above never hears about it.
        title = "untitled"
        emit TitleChanged
      of SavePressed:
        # Raised: saving is not this widget's business.
        emit SaveRequested
    ui.label(ui.id("title"), title, width = fill())

widget shell(title: var string, log: var seq[string]) emits PaneEvent:
  ui.panel(ui.id("root"), cfg(width = fill(), height = fill(), padding = 8)):
    for event in ui.pane(title):
      case event
      of SaveRequested:
        log.add "writing " & title
      of TitleChanged:
        # Not this level's business either: pass it on.
        emit TitleChanged
#+end_src

** Events With Payloads

An enumeration is enough while events carry nothing. An object variant carries what the parent needs, most often the identity of the row that produced it.

#+begin_src nim
import nest

type
  Task = object
    id: int
    title: string
    done: bool

  RowEventKind = enum
    Toggled
    Removed
    Renamed

  RowEvent = object
    id: int
    case kind: RowEventKind
    of Renamed:
      title: string
    else:
      discard

widget taskRow(task: Task) emits RowEvent:
  ui.row(ui.id("root"), cfg(width = fill(), height = fit(), gap = 8, alignItems = Center)):
    ui.checkbox(ui.id("done"), task.title, task.done, width = fill())
    if ui.clicked(ui.id("done")):
      emit RowEvent(id: task.id, kind: Toggled)
    if ui.button(ui.id("rename"), "Rename"):
      emit RowEvent(id: task.id, kind: Renamed, title: task.title & " (copy)")
    if ui.button(ui.id("remove"), "x", width = fixed(24)):
      emit RowEvent(id: task.id, kind: Removed)
#+end_src

** A List Of Children

Each row is scoped by its own identity, so the rows keep their widgets apart, and the parent handles the events of all of them in one loop.

#+begin_src nim
import std/sequtils

import nest

type
  Task = object
    id: int
    title: string
    done: bool

  RowEvent = object
    id: int
    removed: bool

  TaskList = object
    tasks: seq[Task]

widget taskRow(task: Task) emits RowEvent:
  ui.row(ui.id("root"), cfg(width = fill(), height = fit(), gap = 8)):
    ui.checkbox(ui.id("done"), task.title, task.done, width = fill())
    if ui.clicked(ui.id("done")):
      emit RowEvent(id: task.id, removed: false)
    if ui.button(ui.id("remove"), "x", width = fixed(24)):
      emit RowEvent(id: task.id, removed: true)

widget taskList(model: var TaskList):
  ui.column(ui.id("root"), cfg(width = fill(), height = fit(), gap = 4, padding = 8)):
    var emitted: seq[RowEvent]
    for task in model.tasks:
      ui.scope(task.id):
        emitted.add ui.taskRow(task)

    for event in emitted:
      if event.removed:
        model.tasks.keepItIf(it.id != event.id)
      else:
        for task in model.tasks.mitems:
          if task.id == event.id:
            task.done = not task.done
#+end_src

Collecting the rows' events first and editing afterwards keeps the sequence being iterated from changing underneath the loop.

** Siblings

A parent that owns two children is the place where they meet: it turns one child's event into the other child's state.

#+begin_src nim
import nest

type
  SearchEvent = enum
    QueryChanged
    QueryCleared

  ResultsEvent = enum
    ResultChosen

  Browser = object
    query: LineInputState
    results: seq[string]
    chosen: string

widget searchBox(state: LineInputState) emits SearchEvent:
  ui.row(ui.id("root"), cfg(width = fill(), height = fit(), gap = 6)):
    ui.lineInput(ui.id("input"), state, width = fill())
    if ui.submitted(ui.id("input")):
      emit QueryChanged
    if ui.button(ui.id("clear"), "Clear"):
      emit QueryCleared

widget resultList(items: seq[string]) emits ResultsEvent:
  ui.column(ui.id("root"), cfg(width = fill(), height = fit(), gap = 2)):
    for index, item in items:
      ui.scope(index):
        if ui.button(ui.id("item"), item, width = fill()):
          emit ResultChosen

widget browser(model: var Browser):
  ui.column(ui.id("root"), cfg(width = fill(), height = fill(), gap = 8, padding = 8)):
    for event in ui.searchBox(model.query):
      case event
      of QueryChanged:
        model.results = @["match for " & model.query.text]
      of QueryCleared:
        model.query.text = ""
        model.results.setLen(0)

    for event in ui.resultList(model.results):
      case event
      of ResultChosen:
        model.chosen = "chosen"

    ui.label(ui.id("chosen"), model.chosen, width = fill())
#+end_src

** Container Widgets

A parameter of type ~untyped~ takes a block, so a widget can wrap children the caller supplies. A widget with such a parameter expands to a template.

import nest

    ui.label(ui.id("title"), title, width = fill())
    body

widget settingsPage():
  ui.column(ui.id("root"), cfg(width = fill(), height = fill(), gap = 8, padding = 8)):
    ui.titledCard("General"):
      ui.label(ui.id("general"), "General settings", width = fill())
    ui.scope("advanced"):
      ui.titledCard("Advanced"):
        ui.label(ui.id("advanced"), "Advanced settings", width = fill())

A container's children are declared by the caller, so their events belong to the caller too: they are collected in the caller's scope, not the container's.

** Containers That Emit

A container expands to a template, so it cannot use ~emits~. Give it an ~emitted: var seq[E]~ parameter and append to that; the caller passes a sequence it owns, which also means nothing is lost across the two passes.

#+begin_src nim
import nest

type
  PanelEvent = enum
    CloseRequested
    Collapsed

widget closablePanel(title: string, emitted: var seq[PanelEvent], body: untyped):
  ui.card(ui.id("root"), cfg(width = fill(), height = fit(), padding = 8, gap = 6)):
    ui.row(ui.id("head"), cfg(width = fill(), height = fit(), gap = 6, alignItems = Center)):
      ui.label(ui.id("title"), title, width = fill())
      if ui.button(ui.id("collapse"), "-", width = fixed(24)):
        emitted.add Collapsed
      if ui.button(ui.id("close"), "x", width = fixed(24)):
        emitted.add CloseRequested
    body

widget workspace(open: var bool):
  ui.column(ui.id("root"), cfg(width = fill(), height = fill(), gap = 8, padding = 8)):
    if open:
      var emitted: seq[PanelEvent]
      ui.closablePanel("Inspector", emitted):
        ui.label(ui.id("body"), "Panel contents", width = fill())
      for event in emitted:
        case event

** Batching

Because a widget returns every event of the frame, a parent can look at them together before deciding anything.

* State

Each widget owns the state it needs, and a parent holds its children's state as fields. There is no single application model: the root's state is whatever the composition adds up to.

Two rules keep this straight as the tree grows:

- A widget reads its own state and its children's; it writes only through the ~update~ of whichever state it owns.
- A widget never reaches into a sibling's state. Its parent is where two children meet.

* Custom Components

~widget~ composes existing widgets. A component is the other extension point: a ~Component~ subclass that measures, updates and draws itself, attached to a widget with ~ui.component~. Write one when nothing built in draws what is needed.

| Method      | Called                        | Purpose                         |
|-------------+-------------------------------+---------------------------------|
| ~measure~     | before solving, for ~fit~ boxes | report the content's size       |
| ~update~      | once per frame, after solving | react to input                  |
| ~draw~        | when the widget is dirty      | paint inside the widget's frame |
| ~drawOverlay~ | after every ~draw~              | paint above sibling widgets     |

A component that only draws:

#+begin_src nim
import nest
import nest/[coords, resources]

type ProgressBar = ref object of Component
  fraction: float64

proc new(T: typedesc[ProgressBar], fraction: float64): T =
  T(fraction: fraction.clamp(0.0, 1.0))

method measure(self: ProgressBar, resources: Resources): IntrinsicSize =
  intrinsicSize(120, 10)

method draw(self: ProgressBar, widget: Widget, ctx: var DrawContext) =
  let
    f = widget.frame
    track = rect(f.x.toInt, f.y.toInt, f.width.toInt, f.height.toInt)
    filled = rect(f.x.toInt, f.y.toInt, (f.width * self.fraction).toInt, f.height.toInt)
  fillRect(track, ctx.palette.panelMuted)
  fillRect(filled, ctx.palette.primary)
  lineRect(track, ctx.palette.panelBorder)

widget progressBar(fraction: float64, width = fill(), height = fixed(10)):
  discard ui.component(ui.id("bar"), ProgressBar.new(fraction), width, height,
      renderKeyOverride = "progress:" & $fraction)

widget download(progress: float64):
  ui.column(ui.id("root"), cfg(padding = 12, gap = 8)):
    ui.label(ui.id("label"), "Downloading")
    ui.progressBar(progress)

~renderKeyOverride~ tells Nest when the widget must be repainted. A component whose appearance depends on more than its size and alignment has to supply one, or a changed value will not be drawn.

A component that reacts to the pointer derives from ~Interactive~, which also marks its frame as blocking pointer input. Wrapping it in a ~widget~ that emits gives it the same shape as any other widget in the tree.

#+begin_src nim
import nest
import nest/[coords, resources]

type
  Swatch = ref object of Interactive
    value: Color

  SwatchEvent = object
    value: Color

proc new(T: typedesc[Swatch], value: Color): T =
  T(value: value)

method measure(self: Swatch, resources: Resources): IntrinsicSize =
  intrinsicSize(24, 24)

method update(self: Swatch, widget: Widget, ctx: var UpdateContext) =
  let f = widget.frame
  let inside =
    ctx.mouseX.toFloat >= f.x and ctx.mouseX.toFloat < f.x + f.width and
    ctx.mouseY.toFloat >= f.y and ctx.mouseY.toFloat < f.y + f.height
  if inside:
    ctx.setHot(widget.id)
    if ctx.mouseLeftPressed:
      ctx.setActive(widget.id)

  let
    f = widget.frame
    box = rect(f.x.toInt, f.y.toInt, f.width.toInt, f.height.toInt)
  fillRect(box, self.value)
  lineRect(box, if ctx.hot(widget.id): ctx.palette.primary else: ctx.palette.panelBorder)

widget swatch(value: Color) emits SwatchEvent:

    emit SwatchEvent(value: value)

** Animation

import nest
import nest/[coords, resources]

type Spinner = ref object of Component
  discard

proc new(T: typedesc[Spinner]): T =
  T()

method measure(self: Spinner, resources: Resources): IntrinsicSize =
  intrinsicSize(16, 16)

method draw(self: Spinner, widget: Widget, ctx: var DrawContext) =
  let
    f = widget.frame
    step = (ctx.ticks div 120) mod 4
    size = (f.width / 2).toInt
    box = rect(f.x.toInt + (if step in {1, 2}: size else: 0), f.y.toInt + (if step >= 2: size else: 0),
      size, size)
  fillRect(box, ctx.palette.primary)
  ctx.requestRedrawAfter(120)

  discard ui.component(ui.id("spinner"), Spinner.new(), fixed(16), fixed(16))
  ui.markRealtime(ui.id("spinner"))

widget statusLine(busy: bool):

* Growing The Application

The stages below are cumulative, and nothing about the architecture changes between them: a widget is added, it owns its state, and it emits what its parent needs to know.

** Stage 1: One Widget

State, events, ~update~, widget, ~runApp~ — the counter from the top of this file.

** Stage 2: Children Without State

Split by region once one widget declares more than a screenful. A region that owns no state takes what it draws as parameters and emits what it collects.

* Redraws

Frames are event driven. Without input, nothing is drawn. Four calls change that.

| Call                      | Effect                                     |
|---------------------------+--------------------------------------------|
| ~ui.requestRedrawAfter(ms)~ | schedule a frame; the soonest request wins |
| ~ui.markDirty(id)~          | repaint one widget on the next frame       |
| ~ui.markAllDirty()~         | repaint the whole frame                    |
| ~ui.markRealtime(id)~       | repaint this widget every frame            |

~runApp~ marks the frame dirty whenever an event was applied, so a widget only asks for redraws that input does not already cause.

* Dialogs And Overlays

Modal dialogs, menus, popovers, pointer ownership, file pickers, and the out-of-process dialogs that owl programs can open are all covered in [[file:dialogs.org][dialogs.org]].

* The Owl DSL

The second front end compiles nothing. [[https://github.com/dneumann42/owl][Owl]] is a general-purpose command-oriented language, and ~src/nest/owldsl.nim~ defines a DSL in it: a vocabulary of owl commands for widgets, layout, state and events, alongside the language's own. A directory of ~.owl~ files written against that vocabulary is an application, and the ~nest~ executable reads it, runs the same frame loop over the same widgets, watches the files, and reloads the program when one changes.

Nothing about the model from [[*Architecture][Architecture]] is different. The interface is still re-declared every frame, still makes two passes, still lays out through the solver, still identifies widgets by identifier. What changes is who holds the program: in Nim the program is machine code with your types in it, and in owl the program is a syntax tree the runtime walks, with an error dialog instead of a compiler.

Every application in ~apps/~ except the gallery is written this way: ~apps/counter~ is thirty-six lines, ~apps/duck~ is a tabbed text editor with menus, split panes and find-and-replace, and ~apps/layerShellBar~ is a Wayland status bar with a popover project per widget, media controls and live workspace subscriptions.

** A Project

A project is a directory with a ~project.owl~ and a ~main.owl~. ~apps/counter~ is the smallest complete one.

#+begin_example
nest run apps/counter                    # run a project
nest run apps/counter --perf-overlay     # with the frame-timing overlay
nest run apps/counter --benchmark 600    # run 600 frames and print timings
nest generate apps/hello                 # scaffold a project.owl and a main.owl
#+end_example

~project.owl~ is a flat list of bindings, read before the window opens. Every field has a default, and the file may be omitted entirely.

| Field                                 | Meaning                                                     |
|---------------------------------------+-------------------------------------------------------------|
| ~main~                                  | entry point, relative to the project directory (~"main.owl"~) |
| ~title~                                 | window title                                                |
| ~width~, ~height~                         | window size, or the thickness of a docked bar               |
| ~layerShell~                            | ~none~, ~top~, ~bottom~, ~left~, ~right~, or an anchored corner       |
| ~namespace~                             | layer-shell namespace, and the single-instance lock's name  |
| ~theme~                                 | palette name                                                |
| ~exclusiveZone~, ~marginTop~ … ~marginLeft~ | layer-shell geometry                                        |

#+begin_src owl
main = "main.owl"
title = "Counter"
width = 360
height = 220
layerShell = "none"
namespace = "nest-counter"
#+end_src

A ~project.owl~ may ~import~ another file and then use the symbols it defines as field values. ~apps/layerShellBar~ does exactly that: its ~project.owl~ imports ~variables.owl~ and writes ~height = BarHeight~, so the bar's thickness is stated once and read by the layout as well as by the window.

** The Same Application, In Owl

Here is the counter from [[*A Complete Application][A Complete Application]] again: a ~counter~ widget with its own state and its own handlers, and an app around it that keeps the tally.

#+begin_src owl
widget counter key:
  define:
    keyText = eval key
    decrementID = (id keyText "decrement")
    incrementID = (id keyText "increment")
    stepID = (id keyText "step")

  state (string "counter:" keyText):
    count = 0
    step = 1

  events:
    when (clicked decrementID):
      -= count step
      send "counter.changed" count
    when (clicked incrementID):
      += count step
      send "counter.changed" count
    when (clicked stepID):
      set step (pick (= step 1) 5 1)

  column (id keyText "root"):
    width = fit
    height = fit
    gap = 8
    alignItems = Center
    label (id keyText "count") count:
      width = fixed 80
      height = fit
    row (id keyText "controls"):
      width = fit
      height = fit
      gap = 8
      alignItems = Center
      button decrementID "-":
        width = fixed 32
        height = fit
      button incrementID "+":
        width = fixed 32
        height = fit
      button stepID (string "step " step):
        width = fixed 80
        height = fit

state "root":
  changes = 0
  highest = 0
  lowest = 0
  latest = 0
  resetID = (id "reset")

panel (id "root"):
  width = fill
  height = fill
  padding = 16
  gap = 12
  alignItems = Center
  justifyContent = Center
  label (id "title") "Counter":
    width = fit
    height = fit
  counter "app"
  label (id "stats") (string changes " changes, range " lowest " to " highest):
    width = fit
    height = fit
  button resetID "Reset history":
    width = fit
    height = fit

events:
  when (received "counter.changed"):
    set latest (receive "counter.changed")
    += changes 1
    when (> latest highest):
      set highest latest
    when (< latest lowest):
      set lowest latest
  when (clicked resetID):
    set changes 0
    set highest 0
    set lowest 0
#+end_src

Line for line this is the Nim version, with two substitutions. An ~update~ procedure became an ~events~ block that mutates the state in place, since there is no type to case over. And ~emit~ became ~send~, read back by the parent with ~received~ and ~receive~, because owl has no ~emits~, and so no return value to carry events up.

Note where the parent's ~events~ block sits: *after* the tree. Statements evaluate in order, and the widget's own ~events~ block runs while the tree is being declared, so a message sent inside the child is already in the queue by the time the parent's block runs. Both passes evaluate the whole program, so the labels above pick up the new numbers in the layout pass of the same frame.

** The Language

Owl has essentially one syntactic form: a command call. ~+ 1 2~ calls ~+~; parentheses group a call used as an argument; a colon starts an indented body; and indentation without a colon continues the argument list.

#+begin_src owl
; A comment.
fun describe n:
  define:
    doubled = * n 2
    message = "\(n) doubled is \(doubled)"
  print message

fun factorial n:
  if (< n 2):
    1
  else:
    * n (factorial (- n 1))

describe (factorial 5)
#+end_src

The one form that is not a call is a *binding*, ~name = value~. Evaluating a binding does not assign anything: it produces a syntax value, and a command decides what to do with it. ~define~ evaluates bindings and defines them in the current scope, ~state~ treats them as persistent fields, and a widget command treats them as its configuration. This is why ~width = fill~ inside a ~row~ body is not an assignment to a variable called ~width~.

Values are ~nothing~, numbers (always ~float64~), booleans, text, lists, dictionaries, records, syntax, and commands. Only ~nothing~ and ~false~ are false; everything else is true.

A command is a callable value. User-defined ones come in two kinds, which differ in how a parameter is bound *and* in which environment the body runs.

~fun~, ~fn~ and ~lambda~ define argument-evaluating commands. Each argument is evaluated at the call, the parameter is bound to the resulting value, and the body runs in a child of the environment the command was defined in. These are the ones with a closure: they see the definition site.

~command~, ~widget~ and ~block-command~ define raw-syntax commands. A parameter is bound to the unevaluated argument syntax, paired with the caller's environment, and the body runs in a child of the *caller's* environment rather than the definition's. They are not closures — a raw-syntax command resolves free names at the call site, which is why a widget can read the ~state~ fields of the program that declared it without taking them as parameters. Getting an argument's value takes an explicit ~(eval key)~.

| Form                     | Parameter bound to  | Body runs in       | Takes a body  | Use for                        |
|--------------------------+---------------------+--------------------+---------------+--------------------------------|
| ~fun name args:~           | evaluated value     | its defining scope | no            | computation                    |
| ~fn~ / ~lambda~              | evaluated value     | its defining scope | no            | an anonymous function          |
| ~command name args:~       | raw argument syntax | the caller's scope | no            | anything that needs the syntax |
| ~widget name args:~        | raw argument syntax | the caller's scope | no            | a widget                       |
| ~block-command name args:~ | raw argument syntax | the caller's scope | yes, as ~block~ | a container widget             |

~widget~ is exactly ~command~ under another name; the two exist so that a widget declaration reads as one. Every call also binds ~block~ to the call's body and ~layout~ to the text form of how that body was attached, so a raw-syntax command can be handed a whole subtree as data.

The control-flow and data commands are ordinary commands, most of them defined in owl's own prelude:

| Commands                                         | Purpose                   |
|--------------------------------------------------+---------------------------|
| ~if~ / ~else~, ~when~, ~while~, ~cond~, ~pick~, ~and~, ~or~, ~not~ | control flow              |
| ~for item (iter values):~                          | iteration                 |
| ~define~, ~set~, ~+=~, ~-=~, ~*=~, ~/=~                      | binding and assignment    |
| ~list~, ~[]~, ~cons~, ~first~, ~rest~, ~nth~, ~empty?~, ~length~ | lists                     |
| ~dict~, ~{ }~, ~dict-get~, ~dict-put~, ~record~            | keyed data                |
| ~a.b~, ~xs.[0]~                                      | field and index selectors |
| ~open-file~, ~with~, ~read-all~, ~write~                 | files                     |

Nest adds ~string~ for concatenating anything into text, along with ~listAppend~, ~textLines~, ~textFind~, ~textSlice~, ~lineCount~ and ~pathBaseName~, since the prelude is deliberately small.

#+begin_src owl
fun greetings names:
  define:
    labels = list
  for name (iter names):
    set labels (listAppend labels (string "hi " name))
  labels

fun demo:
  define:
    names = []:
      "ada", "grace", "alan"
  print (length (greetings names))

demo
#+end_src

** A Program Is State, Handlers, And A Tree

A Nest owl program is a script, evaluated top to bottom, twice per frame. Three kinds of statement do the work.

*** The state Block

~state "scope": bindings~ declares persistent fields. The first time it runs, each binding's value is evaluated and stored; on every later frame the stored value is restored instead. The names are ordinary bindings in the surrounding scope while the program runs, so handlers read and ~set~ them directly, and the runtime writes their current values back to the store after every ~events~ block and again at the end of the frame.

#+begin_src owl
state "root":
  count = 0
  rootID = id
  incrementID = (id "increment")
#+end_src

The store is keyed by the scope string and the field name, and by nothing else. Two instances of a widget whose ~state~ scope is a constant therefore share one set of fields, which is almost never what is wanted; build the scope from the widget's key instead.

#+begin_src owl
widget counter key:
  define:
    keyText = eval key
  ; Distinct per instance. `state "counter":` would be shared by all of them.
  state (string "counter:" keyText):
    count = 0
  label (id keyText "count") count:
    width = fit
    height = fit
#+end_src

Ids are usually bound in ~state~ as well, so that the handler and the declaration cannot disagree about which widget they mean.

~state~ is also how a program declares its top-level values, because ~define~ cannot. ~define~ raises when the symbol already exists in that scope, and a program's statements are re-evaluated on every pass, so a top-level ~define~ succeeds on the event pass and fails on the layout pass immediately after. It is fine inside a ~fun~ or a ~widget~, where each call gets a fresh scope, and fine in an imported file, which is evaluated once.

*** The events Block

~events:~ is ~ui.events~. Its body runs on the event pass only, and everything that changes state belongs inside one.

| Predicate           | True when                                   |
|---------------------+---------------------------------------------|
| ~clicked id~          | the widget was clicked                      |
| ~middleClicked id~    | it was middle-clicked                       |
| ~submitted id~        | a line input was submitted                  |
| ~focused id~          | it holds focus                              |
| ~keyPressed "escape"~ | a key was pressed this frame                |
| ~external "name"~     | an out-of-frame event was queued under ~name~ |
| ~received "topic"~    | a message is waiting on ~topic~               |

*** Widget Commands

Everything else is a widget. A widget command takes an id, then its positional arguments, then a colon body in which *bindings are its configuration and commands are its children*.

#+begin_src owl
row (id "controls"):
  width = fill          ; configuration
  height = fit
  gap = 8
  alignItems = Center
  label (id "name") "Name":     ; a child
    width = fixed 80
    height = fit
  lineInput (id "value") "":    ; another child
    width = fill
    height = fixed 30
#+end_src

The available commands are ~panel~, ~card~, ~row~, ~column~, ~overlay~, ~center~, ~spacer~, ~table~ and its parts, ~label~, ~button~, ~imageButton~, ~image~, ~checkbox~, ~lineInput~, ~editor~, ~tabs~, ~horizontalSlider~, ~verticalSlider~, ~dialogHeader~, ~modalDialog~, ~menuBar~ and its parts. Size policies are ~fill~, ~fit~, ~fixed n~, ~hug n~ and ~prefer n~; ~insets l t r b~ builds asymmetric padding; ~color r g b~ and ~theme-color "name"~ build colours.

Animations are keyed by widget id and fit the same immediate-mode model. In Nim, call ~ui.animate(id, open, spec)~ or wrap declarations in ~ui.animated(id, open, spec):~. The default specs include ~fadeIn~, ~scaleIn~, ~slideIn~ and ~dialogPopIn~, with curves ~Linear~, ~EaseIn~, ~EaseOut~, ~EaseInOut~, ~SmoothStep~, ~Spring~ and ~BackOut~. Default animations settle at ~DefaultMaxOpacity~ (~0.95~), and each helper accepts ~maxOpacity~ when a different final alpha is needed. In owl, wrap any subtree with ~animation id [open]:~ and set ~duration~, ~curve~, ~fromOpacity~, ~maxOpacity~, ~fromScale~, ~offsetX~ and ~offsetY~ in the body. The widget with that id is still declared normally inside the block:
#+begin_src owl
animation (id "popover"):
  duration = 180
  curve = "backOut"
  fromOpacity = 0
  maxOpacity = 0.95
  fromScale = 0.94
  offsetY = 6
  card (id "popover"):
    width = fill
    height = fill
#+end_src

*** Ids And Scopes

~id~ builds a widget id from its arguments, and ~(id)~ with no arguments generates one. A widget id stringifies back to its own parts, so ids compose: ~id someID "title"~ extends ~someID~. ~scope "key": ...~ is ~ui.scope~, for declaring the same subtree twice.

** Owl Widgets

A widget is a command that declares widgets. The convention throughout ~apps/~ is that its first parameter is a key, every id inside is derived from that key, and the widget is therefore safe to declare more than once.

Because a widget's body runs in the caller's scope, it can read any binding the caller can see. This is the prevailing style in ~apps/duck~: ~duckStatusBar~ takes no parameters at all and reads ~showStatusBar~ and ~statusText~ straight out of the program's ~state "root"~, plus the top-level helper commands beside them. It keeps declarations short, and the cost is that such a widget only works where those names are in scope. Pass a value as a parameter when the widget is meant to be reusable, and read a free name when it is a region of one specific program.

#+begin_src owl
widget labelledValue key labelText valueText:
  define:
    keyText = eval key
  row (id keyText "row"):
    width = fill
    height = fit
    gap = 8
    alignItems = Center
    label (id keyText "label") (eval labelText):
      width = fixed 96
      height = fit
    label (id keyText "value") (eval valueText):
      width = fill
      height = fit

column (id "root"):
  width = fill
  height = fit
  gap = 4
  padding = 8
  labelledValue "name" "Name" "nest"
  labelledValue "version" "Version" "0.0.0"
#+end_src

A container that wraps children the caller supplies is a ~block-command~: the call's body arrives bound to ~block~, and ~eval block~ declares it in place.

#+begin_src owl
block-command titledCard cardID titleText:
  card (eval cardID):
    width = fill
    height = fit
    padding = 10
    gap = 6
    label (id (eval cardID) "title") (eval titleText):
      width = fill
      height = fit
    eval block

column (id "root"):
  width = fill
  height = fill
  gap = 8
  padding = 8
  titledCard (id "general") "General":
    label (id "general" "body") "General settings":
      width = fill
      height = fit
#+end_src

Use ~fun~ for anything that computes, and for a dialog or a section that takes no arguments and only needs to be a name.

** Messages Between Widgets

Owl has no ~emits~, so a widget cannot return its events. It sends them instead. ~send topic payload~ appends to a queue, ~received topic~ says whether the queue has anything, and ~receive topic~ takes the oldest item off it.

#+begin_src owl
; In the child:
events:
  when (clicked saveID):
    send "editor.save" (activeEditorID)

; In the parent, after the child has been declared:
events:
  when (received "editor.save"):
    saveBuffer (receive "editor.save")
#+end_src

Messages are the only channel between widgets that do not share a state scope, and they replace both the returned-event list and the ~emitted: var seq[E]~ parameter of the Nim API. Two things follow from that. Order matters: a parent only sees a message the child sent earlier in the same pass, so its handler goes after the declaration, not before. And nothing consumes a queue automatically, so a topic that is sent to and never received from grows for the life of the program.

** Modules

~import "path.owl"~ evaluates another file's statements in the current environment. The path is resolved relative to the importing file, and each file is imported once no matter how many files ask for it. This is how ~apps/layerShellBar~ shares one ~variables.owl~ across the bar, its six popover projects and every widget file in between.

~use module: include a b c~ is owl's own module command. It takes a bare module name rather than a string, evaluates the file in a child environment, and copies only the named symbols into the caller. ~exclude~ inverts the filter, and ~use module~ with no body binds the whole module as a dictionary named after the file.

#+begin_src owl
import "variables.owl"

use editorWorkspace:
  include editorTree editorWorkspace splitLeaf unsplitLeaf
#+end_src

Choose ~import~ when the file is a shared header of definitions, and ~use~ when it is a module with an interface worth naming. One practical difference: only ~import~ registers the file with the reloader. A change to a file reached by ~import~ reloads the program on the next frame; a change to one reached by ~use~ is not noticed until something else forces a reload.

** Reaching Outside The Frame

Most of what the owl vocabulary adds beyond the widget commands is access to the system around the frame.

| Commands                                                                   | Purpose                              |
|----------------------------------------------------------------------------+--------------------------------------|
| ~shell~, ~shellQuote~                                                          | run a command and read its output    |
| ~shellAsync~, ~shellLaunch~                                                    | run one without blocking the frame   |
| ~clipboardText~, ~copyText~                                                    | the clipboard                        |
| ~clock~, ~formatNow~, ~today-date~, ~date~ and the ~date-*~ helpers                  | time and dates                       |
| ~swayWorkspaces~, ~swayWorkspaceSubscription~, ~swayActiveWindowSubscription~    | live Wayland compositor state        |
| ~pickFile~, ~pickDirectory~, ~pickFileEvent~, ~pickResult~                         | host file pickers                    |
| ~openDialog~, ~toggleDialog~, ~dialogResult~, ~dialogData~, ~closeDialog~            | dialogs as separate processes        |
| ~editorText~, ~setEditorText~, ~editorLine~, ~undoEditor~ and the rest of ~*Editor*~ | drive a text editor widget           |
| ~redrawAfter ms~                                                             | ask for another frame                |
| ~external "name"~                                                            | test for a queued out-of-frame event |

~shell~ blocks the frame and is fine for something short. ~shellAsync key command [intervalMs]~ does not block: it starts the process, returns the last output it has for that key — empty on the very first frame — and re-runs the command once the interval has elapsed. It also asks for the frames it needs to notice that the process finished, so there is no ~redrawAfter~ to pair it with.

#+begin_src owl
state "root":
  battery = ""

events:
  set battery (shellAsync "battery" "cat /sys/class/power_supply/BAT0/capacity" 8000)

label (id "battery") (string battery "%"):
  width = fit
  height = fit
#+end_src

Dialogs, menus and pickers are in [[file:dialogs.org][dialogs.org]].

** Hot Reload And Errors

~main.owl~ and every file reached from it by ~import~ are watched. On Linux the
shared Owl watcher uses inotify to wake an idle Nest process immediately; when
native notifications are unavailable it falls back to periodic file stamps.
The next frame reloads the program — and because a reload builds a fresh
runtime, ~state~ goes back to its declared defaults, so the interface reappears
in its initial state rather than the state it was in.

An error does not end the process. The runtime keeps the last frame that rendered, records the message with the owl stack that reached it, and opens the error dialog in a separate process; clicking a frame in that dialog opens the file at the line. Fixing the file closes the dialog, because the reloader has already noticed the change.

** Owl Against The Nim API

The correspondence is close enough to translate mechanically:

| Nim                               | Owl                                           |
|-----------------------------------+-----------------------------------------------|
| ~widget name(...)~                  | ~widget name ...~                               |
| ~widget name(..., body: untyped)~   | ~block-command name ...~ plus ~eval block~        |
| a plain ~proc~                      | ~fun~                                           |
| a state ~object~                    | a ~state~ block                                 |
| ~proc update(model, event)~         | the body of an ~events~ block                   |
| ~emits E~ and ~emit~                  | ~send topic payload~                            |
| reading a child's returned events | ~received~ and ~receive~                          |
| ~ui.events:~                        | ~events:~                                       |
| ~ui.scope("key"):~                  | ~scope "key":~                                  |
| ~ui.id("a", "b")~                   | ~id "a" "b"~                                    |
| ~cfg(width = fill(), gap = 8)~      | ~width = fill~ and ~gap = 8~ in the widget's body |
| ~runApp(cfg, model, update, root)~  | ~project.owl~ plus ~main.owl~                     |
| ~ui.requestRedrawAfter(ms)~         | ~redrawAfter ms~                                |
| ~import module~                     | ~import "module.owl"~ or ~use module:~            |

Differences that matter in practice:

- *No size defaults.* Every owl widget's configuration starts from ~cfg()~, which is ~fill~ by ~fill~. The per-widget defaults from [[*Sizes Have Defaults][Sizes Have Defaults]] are a Nim-side feature, so a leaf that omits ~height~ in owl gets ~fill~, and a ~fill~ leaf inside a ~fit~ parent collapses to nothing. Write ~width~ and ~height~ on every widget; every program in ~apps/~ does.
- *No typed events.* There is no event enumeration to case over and no compiler to notice a missing branch. A topic name is a string, and a mistyped one silently never arrives.
- *No static types at all.* Numbers are ~float64~, an unknown symbol is a runtime error, and the error surfaces in the dialog rather than at build time.
- *Menus are managed.* Owl's ~menuBar~ reads its whole structure from its body, opens and closes the popover itself, and reports the chosen path through ~menuResult~. The Nim ~menuBar~ is a thin container that leaves all of that to the caller.
- *Dialog processes are owl-only.* ~openDialog~ starts another Nest project as a child process; there is no Nim equivalent.
- *Components cannot be written in owl.* A ~Component~ subclass that measures, updates and draws itself is Nim code. An owl program can compose and animate existing widgets and components with ~animation~, but new component implementations still live in Nim.
- *State resets on reload.* Editing a file restores the declared defaults.

** Using Both

The two front ends are not exclusive. A Nim application can render an owl widget into its own frame with ~renderWidget~, which loads a library file and evaluates one widget against the live ~UI~. The owl part is a child of the Nim part in the same widget tree, laid out by the same solver.

#+begin_src nim
import nest
import nest/owldsl

let runtime = NestOwlRuntime.init()

widget shell():
  ui.row(ui.id("root"), cfg(width = fill(), height = fill(), gap = 8, padding = 8)):
    ui.label(ui.id("nim"), "Written in Nim", width = fixed(140))
    # `sidePanel` lives in a .owl file, and is re-read whenever that file changes.
    runtime.renderWidget(ui, "panels/side.owl", "sidePanel", ["side", "Settings"])
#+end_src

Arguments given as strings arrive in the widget as owl string literals, which is enough for keys and labels. The other overload takes ~SyntaxNode~ values, for a widget whose parameters are lists or dictionaries.

This is the seam for a program that wants types everywhere except one place: a theme, a layout still being designed, a panel the user is expected to edit.

** When To Reach For Which

The choice is not about program size: ~apps/duck~ is written entirely in owl.

Reach for Nim when the state has invariants worth encoding in a type, when a missing ~case~ branch would be a real bug, when the interface needs a ~Component~ subclass to draw something the gallery does not, or when the interface is part of a larger program rather than the whole of it.

Reach for owl when being able to edit a running interface matters more than compile-time checking, when the program spends most of its time moving data between the system and the screen, or when the interface has to be changed by someone who is not going to run a compiler. Both are available in one program: see [[*Using Both][Using Both]].

* Testing A Widget

A widget can be driven without a window: replace the font relays with stubs, build frames by hand, and assert on the events it emitted and the text it drew. Entering the widget's scope gives a test the ids it declared.

#+begin_src nim
import std/strutils

import nest
import nest/screen

type
  Counter = object
    count: int

  CounterEvent = enum
    Bumped

proc update(model: var Counter, event: CounterEvent) =
  case event
  of Bumped: inc model.count

widget counter(model: Counter) emits CounterEvent:
  ui.row(ui.id("root"), cfg(padding = 8, gap = 8)):
    ui.label(ui.id("count"), $model.count, width = fixed(60), height = fixed(24))
    if ui.button(ui.id("inc"), "+", width = fixed(40), height = fixed(24)):
      emit Bumped

when isMainModule:
  var drawn: seq[string]

  fontRelays = FontRelays(
    openFont: proc(path: string, size: int, metrics: var FontMetrics): Font =
      metrics = FontMetrics(ascent: 14, descent: 4, lineHeight: 22)
      Font(size),
    closeFont: proc(f: Font) = discard,
    getFontMetrics: proc(f: Font): FontMetrics =
      FontMetrics(ascent: 14, descent: 4, lineHeight: 22),
    measureText: proc(f: Font, text: string): TextExtent =
      TextExtent(w: max(text.len, 1) * 9, h: 18),
    drawText: proc(f: Font, x, y: int, text: string, fg, bg: Color): TextExtent =
      drawn.add text
      TextExtent(w: max(text.len, 1) * 9, h: 18),
  )

  var
    ui = UI.init()
    model = Counter()
    emitted: seq[CounterEvent]

  ui.initContext(320, 200)
  ui.loadFont("font", "", 18)

  proc frame() =
    drawn.setLen(0)
    ui.markAllDirty()
    ui.layout:
      ui.events:
        emitted.setLen(0)
      # Accumulated, never assigned: the layout pass emits nothing.
      emitted.add ui.counter(model)
      ui.events:
        for event in emitted:
          model.update(event)
    ui.finishInputFrame()

  # First frame: the initial state is drawn, nothing is emitted.
  ui.beginInputFrame()
  frame()
  doAssert "0" in drawn
  doAssert emitted.len == 0

  # The button's id belongs to the widget, so the lookup enters its scope.
  var plusID: WidgetID
  ui.scope("counter"):
    plusID = ui.id("inc")
  let plus = ui.widgetFrame(plusID)
  doAssert plus.ok

  # Press the button. The press is recorded this frame.
  ui.beginInputFrame()
  ui.mouseMove((plus.frame.x + plus.frame.width / 2).int, (plus.frame.y + plus.frame.height / 2).int)
  ui.mouseDown()
  frame()

  # Next frame: the click is observed, emitted, applied, and drawn.
  ui.beginInputFrame()
  frame()
  doAssert emitted == @[Bumped]
  doAssert model.count == 1
  doAssert "1" in drawn

  echo "widget test passed"
#+end_src

* Conventions

** In Nim

- Declare every portion of the interface with ~widget~.
- Give a widget its own event type with ~emits~, named after what happened, not after what the parent should do about it.
- Handle a child's event, or emit one of your own in its place. Never reach past a parent to a grandchild's state.
- A widget owns its state; a parent holds its children's state as fields and calls their ~update~.
- Consume events where they are returned, or accumulate them with ~add~. Never assign them to something that outlives the call.
- Collect a list's events first, edit the list afterwards.
- Mutate nothing outside ~ui.events~.
- Wrap a repeated widget in ~ui.scope~ at the call site.
- Build ids from data, not from a loop index.
- A container takes a ~body: untyped~ parameter, which makes it a template: it cannot use ~emits~, so give it ~emitted: var seq[E]~, and avoid parameter names that also appear as field names in its body.
- Leave sizes alone unless the widget needs a different one; the defaults fit content, fill panes, and give every control the same height.
- Keep ~LineInputState~, ~EditorState~ and ~Mesh2DState~ in the widget's state.
- Reach for a ~Component~ subclass only when nothing built in draws what is needed, and give it a ~renderKeyOverride~ when its appearance depends on more than its size.
- ~import nest~ covers the widget API; ~rect~ and ~point~ come from ~nest/coords~, and ~Resources~ from ~nest/resources~.

** In Owl

- Declare every portion of the interface with ~widget~, and take a key as its first parameter.
- Derive every id inside a widget from that key, so the widget can be declared twice.
- Build a ~state~ scope from the key too; a constant scope is shared by every instance.
- Bind ids in ~state~ rather than repeating ~id ...~ in both the handler and the declaration.
- Remember that a ~widget~ body runs in the caller's scope. Take a parameter for anything the widget should be reusable over, and read a free name only where the widget belongs to one program.
- Put ~width~ and ~height~ on every widget. There are no per-widget defaults on this side.
- Mutate nothing outside an ~events~ block.
- Put a parent's ~events~ block after the children it listens to, so a message sent this frame arrives this frame.
- Clear what you read: ~clearMenuResult~, ~clearDialogResult~, ~clearPickResult~. A result that is never cleared re-fires every frame.
- Prefer ~shellAsync~ to ~shell~ for anything that is not instant.
- Use ~import~ for shared definitions and ~use~ for modules with an interface; remember that only ~import~ is watched for reload.
